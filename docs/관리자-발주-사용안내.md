# 관리자 주문 · 발주 관리

## 접속

- 개발: http://localhost:3000/admin
- 배포 후: `https://도메인/admin`
- 관리자 계정으로 로그인한 경우 내 계정 보관함에도 `관리자 페이지 →` 링크가 표시됩니다.

현재 Supabase와 OAuth 앱이 아직 생성/연결되지 않았습니다. 화면은 볼 수 있지만 실제 주문 정보와 PDF는 **DB 연결 및 관리자 등록 후** 사용할 수 있습니다. 가짜 주문이나 접근 우회 기능은 넣지 않았습니다.

## 처음 한 번 연결

1. 먼저 `docs/회원-로그인-DB-연결.md`에 따라 Supabase와 카카오·Google 로그인을 연결합니다.
2. SQL Editor에서 기존 회원 DB 마이그레이션 다음으로 `supabase/migrations/202611040002_admin_fulfillment.sql`을 실행합니다.
3. 사이트에서 본인 계정으로 한 번 로그인합니다.
4. Supabase Authentication → Users에서 본인의 정확한 User UID를 확인합니다.
5. SQL Editor에서 다음 SQL의 UID를 본인 것으로 바꿔 실행합니다.

```sql
insert into public.admin_members(user_id)
values ('본인의-User-UID')
on conflict(user_id) do update set enabled=true;
```

관리자 권한은 이메일이나 수정 가능한 프로필 정보로 판단하지 않습니다. 회원이 본인에게 관리자 권한을 줄 수 없으며, DB에서 등록한 UID만 허용합니다.

권한 해제:

```sql
update public.admin_members set enabled=false where user_id='해제할-User-UID';
```

## 매일 아침 발주 순서

1. `/admin`의 **발주할 것**을 엽니다. 오래된 주문부터 표시합니다.
2. `주문 열기` → 고객 정보, 받는 분 연락처·주소·배송 메모를 확인합니다.
3. `포토북 PDF 다운로드`로 파일을 받습니다. 최초에는 생성 후 비공개 저장소에 보관하고, 이후에는 보관 파일을 다시 내려줍니다.
4. 파일을 확인하고 제작소에 직접 발주합니다.
5. 제작소명·발주 번호 등을 메모하고 `제작소에 발주 완료`를 누릅니다.
6. 주문이 **발주 완료 · 배송 중**으로 이동하고 발주 시간이 기록됩니다.

`발주 완료`는 **수동 발주를 기록하는 버튼**입니다. 제작소로 메일/메시지를 보내거나 결제를 실행하지 않습니다. 현재 PG가 연결되지 않았으므로 `주문 요청` 상태의 결제 여부도 별도로 확인합니다.

## 송장과 배송

1. 발주 완료 · 제작 중 주문을 엽니다.
2. 택배사와 송장번호를 입력하고 `송장 저장 · 배송 시작`을 누릅니다.
3. 주문이 배송 중으로 바뀌며, 소비자의 `/account` 주문·배송 화면에도 반영됩니다.
4. 실제 도착을 확인한 뒤 `배송 완료로 표시`를 누르면 **배송 완료 · 취소** 구분으로 이동합니다.

택배사 실시간 추적과 자동 배송 완료 판정은 아직 연결하지 않았습니다. 모든 처리 시점과 관리자 작업은 DB에 기록됩니다. 동시에 열린 화면에서 중복 처리하려 하면 새로고침을 요구합니다.

## PDF 서버 설정

`.env.local`과 배포 서버 환경변수:

```dotenv
SITE_URL=http://localhost:3000
# 운영 시 실제 HTTPS 도메인으로 변경
# PDF_BROWSER_EXECUTABLE=서버의/Chromium/실행파일
```

개발 모드의 SITE_URL 기본값은 localhost:3000입니다. 서버는 요청 헤더의 임의 주소를 사용하지 않고 위 신뢰된 사이트 주소만 열어 PDF를 생성합니다.
Windows에서는 설치된 Edge를 자동으로 찾아 사용합니다. 다른 서버에서는 다음으로 Chromium과 필요한 시스템 라이브러리를 설치하거나 `PDF_BROWSER_EXECUTABLE`로 실행 경로를 지정합니다.

```sh
npx playwright install --with-deps chromium
```

PDF 생성은 Chromium 실행과 충분한 메모리/실행 시간을 지원하는 Node.js 서버에서 동작합니다. 서버 브라우저는 사이트 내부 페이지와 사진 프록시만 요청할 수 있고, 각 요청마다 관리자 권한을 다시 확인합니다.

## 제작 파일 형식

- 앞표지 → 내지 → 뒷표지 순서의 한 파일입니다.
- 실제 디자인 컴포넌트와 원본 사진을 사용합니다. 이미지 확대·이동 구도도 반영합니다.
- 재단 211×211mm + 사방 3mm 여유분 = **217×217mm**.
- 사진·폰트가 준비되지 않으면 생성 실패로 처리하며, 사진 없는 파일을 성공으로 보관하지 않습니다.
- 주문 당시 확정 원고·배송지·원본 사진 참조를 사용합니다. 소비자의 이후 회원정보/배송지 변경은 주문 주소에 영향을 주지 않습니다.
- 제본용 **앞·책등·뒤 표지 펼침**은 제작소의 종이/쪽수별 책등 두께와 표지 사양을 받아 별도 확정해야 합니다. 현재 PDF에는 앞·뒤 표지가 개별 쪽으로 들어 있습니다.
- 제작소가 요구하는 CMYK·PDF/X·표지 펼침·최소 쪽수·내지 제본 방식은 실제 제작소 사양으로 확인합니다. 현재 파일은 Chromium의 RGB PDF 출력입니다.

서버 템플릿 변경으로 PDF를 새로 발행할 때는 `lib/admin/pdf.ts`의 `PDF_TEMPLATE_VERSION`을 올려 기존 발행 파일을 덮어쓰지 않도록 관리합니다.

## 권한과 데이터

- `admin_members`: 관리자 등록. 일반 회원에게 읽기/쓰기 권한 없음.
- `orders`: 발주 시각·관리 메모·상태 변경 버전.
- `shipments`: 송장과 발송/도착 시각.
- `order_documents`: 주문별 PDF 파일 기록.
- `order_admin_events`: 발주·송장·배송 완료·PDF 생성·메모 변경 이력.
- `order-pdfs`: 비공개 PDF 저장소. 관리자만 접근 가능.
- 관리자 사진 접근은 주문 스냅샷에서 참조하는 파일에 한정합니다. 다른 비공개 작업 사진 전체를 공개하지 않습니다.

## 검증

```sh
npm run test:db
npm run build
```

DB 테스트는 실제 마이그레이션을 PGlite(PostgreSQL)에 적용해 관리자 권한, 자기 권한 상승 차단, 주문 분류, 송장 필수 입력, 중복 처리 방지, PDF/사진 접근, 권한 해제 후 접근 차단을 확인합니다.
브라우저 검증은 격리된 테스트 주문으로 모바일/PC 관리 흐름과 두 디자인의 PDF 페이지 수·크기·이미지·텍스트 렌더를 확인했습니다. 실제 Supabase 버킷 업로드와 관리자 OAuth 세션을 사용하는 서버 PDF 다운로드는 연결 후 첫 실제/테스트 주문으로 최종 확인해야 합니다.
